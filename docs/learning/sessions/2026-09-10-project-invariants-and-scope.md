## 질문과 내 답변

### 질문 1: 핵심 불변조건 다섯 가지와 위반 결과

**내 답변 요지**

- 처음에는 정합성, 동시성, 고가용성, JWT, 트랜잭션을 불변조건으로 들었다.
- 동시성이 깨지면 실제 재고보다 많이 주문될 수 있다고 답했다.
- 정합성이나 트랜잭션이 깨지면 dirty checking이 발생한다고 답했다.
- 힌트 후 재고, 동일 요청, 취소 소유권, 실패 요청 재시도, 커밋 이후 캐시 삭제 조건을 순서대로 확인했다.

**맞은 부분**

- 동시 주문에서 초과 판매가 발생할 수 있다는 위험을 구체적으로 연결했다.
- 같은 사용자의 동일 요청은 한 번만 처리해야 한다는 방향을 잡았다.
- 주문 취소 전에 사용자와 주문 소유자를 비교해야 한다고 설명했다.
- MariaDB 롤백과 Redis 변경이 하나의 트랜잭션으로 함께 되돌아가지 않는다는 점을 이해했다.

**보완하거나 잘못 이해한 부분**

- 정합성·동시성·고가용성은 넓은 목표나 품질 속성이고, JWT·트랜잭션은 구현 수단이다.
- 재고는 `0 이하`가 아니라 `0 미만`이 되면 안 된다. 재고 0은 정상이다.
- dirty checking은 JPA 변경 감지 기능이지 정합성 실패의 결과가 아니다.
- 커밋 전 캐시 무효화는 Redis에 변경 상품 값을 쓰는 동작이 아니라 기존 캐시를 삭제하는 동작이다.
- 세션 중 `PROCESSING` 키가 남으면 현재 구현이 재시도를 거절한다고 안내했으나 코드 확인 결과 잘못된 설명이었다. 현재 코드는 선점 실패만으로 거절하지 않고 DB 확인·상품 락 경로를 계속하며 DB 유일 제약을 최종 방어선으로 사용한다. `[CODE]`

**교정된 답변**

- 재고는 음수가 될 수 없고 동시 주문에서도 실제 수량보다 많이 판매해서는 안 된다.
- 같은 사용자·멱등성 키·payload의 재요청은 새 주문을 생성하지 않고 기존 결과를 반환해야 한다.
- 실패한 요청은 자신이 소유한 처리 토큰만 정리해 재시도를 허용해야 한다.
- 주문 소유자만 주문을 취소할 수 있고 중복 취소로 재고를 두 번 복구해서는 안 된다.
- 상품 캐시는 DB 커밋 이후에 삭제해야 한다.
- 대기열 활성 권한은 사용자와 상품 범위가 일치해야 하고 책임지는 권한만 정리해야 한다.

### 질문 2: 프로젝트 한 문장 소개

**내 답변 요지**

> 백엔드에 중점을 두고 단순 기능보다 정합성과 동시성 문제 해결에 집중했으며, 재고 같은 데이터를 정확하게 지키는 프로젝트라고 설명했다.

**피드백**

- `Spring Boot 기반 이커머스 백엔드 PoC`라고 성격을 명확히 하고, 재고 초과 판매와 중복 주문이라는 구체적인 문제를 앞에 둔다.
- 재고는 사용자 개인 데이터가 아니라 여러 요청이 함께 변경하는 공유 상태다.

### 질문 3: 구현하지 않았거나 검증하지 못한 범위

**내 답변 요지**

> 서버에 배포하지 않아 운영 데이터가 없고 결제 시스템이 추가되지 않았다고 답했다.

**피드백**

- 실제 운영 배포 경로, 운영 트래픽과 데이터가 없으므로 운영 용량·고가용성·SLO를 보장할 수 없다.
- 결제 승인·취소, 정산, 배송이 없으므로 완성형 쇼핑몰이나 결제 시스템으로 소개하지 않는다.
- 로컬 반복 부하 결과는 특정 환경의 실험이지 운영 성능 보장이 아니다.

## 오늘의 핵심 오개념

- 불변조건은 정합성·동시성 같은 추상어 또는 JWT·트랜잭션 같은 수단이 아니라 참과 거짓을 판정할 수 있는 규칙이어야 한다.
