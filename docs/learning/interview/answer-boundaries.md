# 면접에서 지켜야 할 답변 경계

- 분류: 면접
- 관련 역량 ID: P17

기술의 장점만 말하지 않고 선택 기준, 검증 조건과 보장하지 못하는 범위를 함께 설명한다. 아래 문장은 암기용 모범 답안이 아니라 과장을 발견하기 위한 기준이다.

| 피해야 할 표현 | 문제 | 더 정확한 방향 |
|---|---|---|
| Redis 락이라서 DB 락보다 빠릅니다. | 다른 workload를 일반화함 | 락 대기를 DB 트랜잭션 밖으로 옮겨 connection 점유를 줄이려는 선택이라고 설명 |
| 분산 락으로 동시성 문제를 완벽하게 해결했습니다. | Redis 단절, JVM 정지와 fencing 부재를 무시함 | 지원 주문 경로의 동시 차감을 직렬화했고 남은 실패 모드를 설명 |
| DB CHECK로 초과 판매를 모두 막습니다. | CHECK는 음수 저장만 직접 차단함 | 도메인 검증·락·DB 제약의 역할을 분리해 설명 |
| No-Offset은 데이터가 많아도 일정한 속도입니다. | 필터 선택도와 인덱스를 무시함 | offset scan과 count를 줄이지만 실행 계획에 의존한다고 설명 |
| 대기열로 동시 접속자 수를 완벽히 제한합니다. | active TTL은 실행 슬롯이 아님 | 상품별 admission 권한의 발급 속도를 제어한다고 설명 |
| 멱등성은 Redis SET NX로 보장합니다. | TTL·장애·commit 후 cache 실패를 무시함 | Redis는 최적화, DB unique는 최종 방어선이라고 설명 |
| 무중단 배포를 구현했습니다. | health gate·rollback·운영 검증이 없음 | CI 검증과 이미지 게시까지 자동화됐다고 범위를 제한 |
| k6 결과가 이 서버의 최대 처리량입니다. | 로컬 단일 조건의 반복 결과임 | 동일 환경의 회귀 baseline이라고 설명 |
| 테스트가 모두 통과해서 운영 장애가 없습니다. | 테스트 범위 밖 실패를 배제함 | 테스트가 판정한 조건과 미검증 범위를 함께 설명 |
| 금융 결제 시스템을 구현했습니다. | 결제 승인·취소·정산·외부기관 연동이 없음 | 커머스 주문·재고 PoC이며 금융과 공통인 정합성 문제를 다뤘다고 설명 |
| Flyway로 운영 스키마를 관리합니다. | 현재 결정과 다름 | 운영 데이터가 없는 현재는 Hibernate update이며 전환 조건을 설명 |

## 답변 점검 질문

1. 이 문장에서 실제로 테스트한 조건은 무엇인가?
2. 특정 환경의 결과를 보편적인 장점으로 확대하고 있지 않은가?
3. 정상 흐름만 설명하고 외부 의존성 장애를 생략하지 않았는가?
4. 현재 구현과 향후 보완 방향을 섞지 않았는가?
5. 선택하지 않은 대안과 그 이유를 설명할 수 있는가?
