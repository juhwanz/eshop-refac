# 상품 단위 Redis admission queue를 사용한다

- 상태: 채택
- 날짜: 2026-09-08

## 배경

기존 전역 대기열은 한 상품의 혼잡이 다른 상품 주문까지 막고, millisecond 등록 시각을 ZSet score로 사용해 같은 시각 요청의 순서를 결정적으로 보장하지 못한다. 사용자 단위 활성 키는 허용받은 상품과 실제 주문 상품이 일치하는지도 확인할 수 없다.

판매 이벤트 도메인이나 실시간 알림까지 확장하지 않고, 상품별 입장 속도를 제어하는 최소 대기열 계약이 필요하다.

## 결정

- 대기열과 활성 권한의 범위를 `productId + userId`로 정한다.
- 상품별 waiting ZSet의 score는 Redis `INCR`로 발급한 단조 증가 sequence를 사용한다. 중복 등록은 기존 member를 반환하고 sequence를 새로 발급하지 않는다.
- 활성 권한은 상품별 ZSet에 만료 시각을 score로 저장한다. Redis 서버 시간을 기준으로 유효성을 판단하고 만료 member를 조회와 승격 과정에서 정리한다.
- 등록과 승격은 Lua script로 처리한다. 승격 시 waiting 제거와 active 추가가 함께 성공하도록 원자화한다.
- 대기자가 있는 상품은 전역 `queue:waiting-products` ZSet에 두고, 스케줄러는 매 실행마다 제한된 상품만 순환 처리한다. 전체 키 공간에 `KEYS`를 실행하지 않는다.
- 스케줄러는 상품마다 일정 인원을 활성화한다. 이는 admission rate 제어이며 동시 실행 수 보장은 아니다.
- 주문은 상품 락을 획득하고 완료 주문을 재확인한 뒤 `userId + productId` 활성 권한을 검사한다. 완료된 멱등 요청은 권한을 검사하거나 소비하지 않는다.
- 락 획득 실패와 락 대기 interrupt는 권한을 보존한다. 권한 확인 후 주문을 시도했다면 결과와 관계없이 해당 상품 권한을 소비한다.
- 현재 단일 Redis에서 상품별 키와 전역 상품 인덱스를 함께 다루는 원자성을 우선한다. 상품 키에 `{productId}` 표기를 사용하지만 전역 인덱스 때문에 Redis Cluster 호환성을 보장하지 않는다.

## 검토한 대안

- 전역 대기열 유지: 구현 변경은 작지만 상품 간 격리와 상품 권한 검증을 제공하지 못한다.
- 등록 시각을 ZSet score로 유지: 별도 sequence 키가 필요 없지만 같은 millisecond 요청은 member 문자열 순서로 정렬된다.
- 사용자별 active String 키: 개별 Redis TTL은 단순하지만 한 번의 상품 승격 script에서 동적으로 생성되는 여러 키를 다뤄야 하며 상품 단위 상태 조회와 정리가 분산된다.
- Redis `KEYS` 또는 매번 전체 상품 조회: 별도 인덱스는 필요 없지만 Redis 또는 DB 데이터 증가에 따라 한 번의 스케줄 실행량을 제한하기 어렵다.
- 활성 권한을 멱등성 키와 결합: 실패 후 권한 소유권을 더 정밀하게 판단할 수 있지만 클라이언트 계약과 상태 모델이 커져 MVP 범위를 넘는다.

## 결과

- 한 사용자가 여러 상품 대기열과 활성 권한을 독립적으로 가질 수 있고, 상품 A 권한으로 상품 B를 주문할 수 없다.
- 동일 시각과 동시 등록에서도 Redis가 실행한 순서대로 고유 sequence가 부여된다.
- 대기 제거와 활성 권한 발급은 부분 적용되지 않으며, 스케줄러가 한 번에 조회하는 상품과 사용자 수가 제한된다.
- 활성 권한은 동시 실행 슬롯이 아니다. TTL 동안 사용되지 않은 권한이 남을 수 있고 실제 처리량은 주문 시간과 락 경합에도 영향을 받는다.
- 주문을 시도한 뒤 시스템 오류가 발생하면 다시 대기열에 등록해야 한다. 같은 요청의 중복 주문은 DB 멱등성 제약으로 방지한다.
- Redis Cluster를 도입할 때는 전역 상품 인덱스와 상품별 Lua 원자성 경계를 다시 설계해야 한다.
- 구현과 회귀 검증은 [#22](https://github.com/juhwanz/eshop-refac/issues/22)에서 추적한다.
