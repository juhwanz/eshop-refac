# 재고 보호에 Redisson watchdog과 DB CHECK를 사용한다

- 상태: 채택
- 날짜: 2026-09-08

## 배경

주문과 취소의 상품별 Redis 락에 고정 3초 lease를 사용하면 DB 트랜잭션이 끝나기 전에 락이 만료되어 다른 요청이 진입할 수 있다. 또한 도메인 재고 검증을 우회한 직접 SQL 쓰기에도 음수 재고를 차단할 DB 제약이 필요하다.

## 결정

- 주문과 취소 모두 lease 없는 `tryLock(waitTime, unit)`을 사용하고 Redisson watchdog으로 락을 갱신한다. 운영 watchdog timeout은 기본 30초를 사용한다.
- 상품별 락은 쓰기 트랜잭션 전에 획득하고 커밋 또는 롤백 이후 현재 소유 스레드만 해제한다. 락 대기 중 DB 커넥션을 점유하지 않는 경계를 유지한다.
- 락 획득 실패와 interrupt 시 주문 활성 권한을 보존한다. 락을 획득한 주문 경로만 해당 사용자의 활성 권한을 정리하고 취소 경로는 정리하지 않는다.
- Product 매핑에 `chk_products_stock_nonnegative` CHECK를 선언해 `stock_quantity >= 0`을 DB에서도 검증한다. 기존 도메인 검증은 유지한다.
- ADR-0002의 Hibernate schema 관리 방침은 유지한다. 기존 테이블에는 `ddl-auto: update`가 CHECK를 추가하지 않으므로 명시적 DDL로 적용한다. 자동 데이터 초기화나 보정은 하지 않는다. 적용 SQL과 확인 절차는 [재고 보호 문서](../stock-protection.md)에 둔다.

## 검토한 대안

- 고정 lease 확대: 변경은 작지만 실행 시간이 설정값을 초과할 위험을 남긴다.
- DB 비관적 락으로 통일: DB에서 직렬화할 수 있지만 락 대기 중 커넥션을 점유한다. 이번에는 기존 Redis 락 경계를 유지한다.
- 애플리케이션 검증만 유지: 직접 SQL 등 우회 쓰기에서 음수 재고를 차단하지 못한다.

## 결과

- 정상적으로 watchdog 갱신이 가능한 환경에서 긴 주문·취소 트랜잭션을 보호하며 음수 재고 쓰기는 DB가 거절한다.
- watchdog 갱신은 Redis 통신과 JVM 실행에 의존한다. 장시간 JVM 정지나 Redis 통신 장애에서 완전한 상호 배제를 보장하지 않는다.
- CHECK는 음수 저장을 막지만 갱신 유실에 의한 초과 판매까지 막지 못한다. 모든 장애 상황의 재고 정합성을 보장한다고 주장하지 않는다.
- 고정 lease가 없어 정상 프로세스의 멈추지 않는 작업은 락을 계속 유지할 수 있다. 작업 시간 제한이나 추가 장애 방어가 필요해지면 별도로 설계한다.
- 기존 DB 제약 적용은 사용자 수행으로 완료됐으며, 자동 검증은 Testcontainers MariaDB·Redis 환경에서 수행했다.
- 구현과 회귀 검증은 [#12](https://github.com/juhwanz/eshop-refac/issues/12)에서 추적한다.
