# 로그인 실패는 별도 트랜잭션의 임시 잠금으로 제한한다

- 상태: 채택
- 날짜: 2026-09-08

## 배경

기존 로그인 로직은 같은 트랜잭션에서 실패 횟수를 증가시킨 뒤 예외를 던져 변경을 롤백한다. 실패 횟수만 영속화하면 만료 정보가 없는 `LOCKED` 상태로 전환되어 공격자가 이메일을 아는 것만으로 다른 사용자를 영구 잠글 수 있다. 동시에 발생한 실패가 같은 횟수를 읽고 덮어쓰는 갱신 유실도 방지해야 한다.

OWASP는 계정별 실패 횟수, 관찰 구간과 잠금 기간을 함께 고려하고 계정 서비스 거부 위험을 줄이도록 권고한다. NIST SP 800-63B는 계정별 연속 실패 제한과 성공 인증 후 실패 횟수 초기화를 요구한다. 두 지침 모두 이 서비스의 구체적인 임계치와 기간을 정하지 않으므로 현재 위험과 기존 동작에 맞는 초기값을 선택한다.

## 결정

- 임시 로그인 잠금은 계정 생명주기 상태와 분리하여 `loginFailCount`와 `lockedUntil`로 관리한다.
- 초기 기본값은 연속 5회 실패와 15분 잠금이며 `app.security.login-lock` 설정으로 변경할 수 있다. 5회는 기존 정책을 유지하고, 15분은 반복 대입을 지연하면서 영구적인 계정 서비스 거부를 피하기 위한 시작값이다.
- 활성 잠금 중 요청은 실패 횟수나 만료 시각을 연장하지 않는다. 만료 후 첫 요청은 새 실패 주기로 처리하며 성공하면 실패 상태를 초기화한다.
- 비밀번호 검증은 DB 락 밖에서 수행한다. 로그인 상태 반영은 별도 `REQUIRES_NEW` 트랜잭션에서 사용자 행을 비관적 쓰기 락으로 조회한 뒤 수행한다.
- 로그인 메서드는 바깥 DB 트랜잭션을 사용하지 않아 별도 트랜잭션 대기 중 커넥션을 이중 점유하지 않는다.
- 사용자 없음, 비밀번호 불일치, 잠금과 비활성 상태는 외부에 동일한 `LOGIN_FAILED` 응답으로 반환한다.

## 검토한 대안

- 기존 `LOCKED` 상태만 영속화: 변경은 작지만 자동 해제 정보가 없어 계정 서비스 거부 공격에 취약하다.
- 조건부 원자 SQL update: 락 점유를 더 줄일 수 있지만 성공, 실패, 잠금 만료의 경합 규칙이 SQL에 분산되고 검토 복잡도가 커진다.
- 로그인 전체를 비관적 락 트랜잭션으로 처리: 구현은 단순하지만 비용이 큰 비밀번호 해시 동안 행 락과 DB 커넥션을 점유한다.
- Redis 카운터: 빠른 만료 처리가 가능하지만 로그인 보안 상태의 최종 기준이 Redis 가용성과 데이터 보존에 의존한다.

## 결과

- 실패 응답으로 로그인 트랜잭션이 롤백되어도 실패 기록이 유지되고 동일 계정의 동시 실패는 직렬화된다.
- 잠금은 자동으로 만료되며 공격자의 추가 요청으로 잠금 기간이 무기한 연장되지 않는다.
- 같은 계정의 상태 변경은 짧게 직렬화되지만 다른 계정의 로그인은 서로 차단하지 않는다.
- 비밀번호 변경 기능이 추가되면 락 밖에서 읽은 비밀번호 해시와 상태 반영 사이의 경합을 재검토해야 한다.
- 계정별 임시 잠금만 제공한다. IP 기반 제한, CAPTCHA, MFA와 위험 기반 인증은 별도 범위다.
