# 반복 가능한 baseline으로 부하 테스트 기준을 관리한다

- 상태: 채택
- 날짜: 2026-09-09

## 배경

상품 대기열과 주문·조회 경쟁을 재현하는 부하 테스트는 실행 환경, 애플리케이션 워밍업, DB 커넥션 풀과 로컬 가상화 조건에 따라 결과가 크게 달라질 수 있다. 근거 없이 정한 지연시간이나 오류율을 합격 기준으로 사용하면 실제 회귀를 놓치거나 정상 변경을 실패로 판단할 수 있다.

현재 프로젝트에는 운영 트래픽과 용량 계획에 근거한 SLO가 없다. 따라서 운영 목표를 선언하지 않으면서도 동일 조건에서 성능 퇴행을 발견할 수 있는 검증 기준이 필요하다.

## 결정

- 부하 테스트는 threshold 없이 측정하는 `baseline` 프로필과 기준을 적용하는 `regression` 프로필로 분리한다.
- baseline은 동일한 애플리케이션 commit, 실행 환경, 데이터 규모, VU와 duration에서 최소 3회 반복한다.
- 각 실행은 동일한 초기 재고를 가진 격리 상품을 사용하고 성공 주문 수와 최종 재고의 불변조건을 함께 검증한다.
- 주문 성공, 대기, 멱등성 충돌, 재고 부족과 시스템 오류를 구분한다. 시스템 오류율은 전체뿐 아니라 대기열·주문·조회 작업별로 기록한다.
- 로컬 회귀 threshold는 반복 측정의 가장 나쁜 p95와 오류율에 명시적인 여유를 더해 정한다. 환경이나 workload가 바뀌면 기존 수치를 그대로 재사용하지 않고 baseline을 다시 측정한다.
- 원본 결과와 테스트 자격 증명은 Git에서 제외하고, 비밀정보가 없는 실행 조건·대표 결과·선정 근거만 문서에 기록한다.
- 이 threshold는 동일 환경의 회귀 감지 기준이며 운영 SLO, 최대 처리량 또는 용량 보장이 아니다.

## 검토한 대안

- 측정 전에 목표 수치를 임의로 고정: 바로 사용할 수 있지만 현재 시스템과 실행 환경의 실제 분포를 반영하지 못한다.
- 운영 SLO로 정의: 명확한 목표를 제공하지만 운영 트래픽, 사용자 기대와 용량 자료가 없어 현재 단계에서는 근거가 부족하다.
- threshold 없이 결과만 보관: 잘못된 합격 기준은 피하지만 이후 변경의 자동 회귀 판단이 어렵다.
- 한 번의 baseline만 사용: 비용은 작지만 워밍업과 로컬 자원 변동에 크게 좌우될 수 있다.

## 결과

- threshold의 출처와 적용 범위가 명확해지고 동일 조건의 성능 회귀를 자동으로 감지할 수 있다.
- 재고 불변조건과 예상된 비성공 응답을 성능 실패와 혼동하지 않는다.
- 반복 측정과 격리 상품 준비 비용이 발생하며 로컬 환경의 변동성이 크면 기준도 느슨해질 수 있다.
- 운영 SLO가 필요해지면 실제 트래픽과 용량 자료를 바탕으로 별도 결정을 기록해야 한다.
- 구현, baseline과 대표 결과는 [#17](https://github.com/juhwanz/eshop-refac/issues/17)에서 추적한다.
