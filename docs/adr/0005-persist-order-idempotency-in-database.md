# 주문 멱등성의 최종 기준을 DB에 둔다

- 상태: 채택
- 날짜: 2026-09-08

## 배경

Redis 완료 응답만으로는 TTL 만료 또는 DB 커밋 뒤 캐시 저장 실패에서 중복 주문을 막을 수 없다.
같은 키의 다른 payload도 구분해야 한다. 현재 응답은 orderId 하나이며 주문 물리 삭제 API는 없다.

## 결정

- orders에 요청 키와 payload fingerprint를 저장하고 `(user_id, idempotency_key)`를 DB에서 유일하게 보장한다.
- 요청 키는 ASCII 1~128자의 원문 바이트로 저장하여 대소문자를 구분한다. fingerprint는 버전이 포함된 상품 ID·수량의 SHA-256이다.
- 주문·멱등성 정보·재고 차감은 같은 트랜잭션으로 커밋하거나 롤백한다. 유일 제약 경합의 결과 복구는 롤백된 트랜잭션 밖에서 수행한다.
- Redis는 완료 응답 최적화 계층이며 cache miss 및 장애 시 DB 결과를 조회한다. 캐시 쓰기 실패가 커밋된 주문 성공을 뒤집지 않는다.
- 상품 락은 트랜잭션 진입 전에 획득한다. 기존 결과를 재확인한 뒤 신규 주문에만 대기열 검증을 적용한다.
- 키는 주문과 함께 보존하며 취소 후에도 재사용하지 않는다. 별도 상태 머신, 복구 워커, outbox 및 Flyway는 추가하지 않는다.

## 검토한 대안

- 별도 멱등성 테이블: 독립적인 보존이 가능하지만 현재 응답과 보존 요구에는 추가 엔티티·FK·저장 절차가 불필요하다.
- Redis TTL 연장: 유실 및 커밋 이후 실패에 대한 DB 방어선을 제공하지 못한다.
- DB 처리 상태와 복구 워커: 주문과 결과를 한 트랜잭션에 저장할 수 있어 현재는 필요하지 않다.

## 결과

- 캐시가 없어도 기존 주문을 복구하고 다른 payload의 키 재사용을 거절한다.
- 주문 삭제 시 멱등성 보장도 종료된다. 추후 물리 삭제·독립 보존 요구가 생기면 재검토한다.
- Redis 전체 장애 시 신규 주문 가용성은 기존 분산 락과 대기열에 의존한다.
- 기존 키 없는 주문에는 멱등성 정보를 소급 복원하지 않는다.
- 키 계약, 보존 및 기존 DB 적용 확인은 [주문 멱등성 문서](../order-idempotency.md), 작업 범위는 [#13](https://github.com/juhwanz/eshop-refac/issues/13)에서 추적한다.
